# Firestore data model and ownership

This is a logical model inferred from source. Firestore is schemaless, so field
contracts must ultimately be backed by validators and representative non-private
fixtures. Collection names listed here are the stable navigation keys for code
search.

## Core resident and access data

| Collection/document | Owning domain | Main writers | Main readers |
|---|---|---|---|
| `residents` | Residents | resident sync/update APIs | auth, LPR, visitor, payments, surveys |
| `resident_pins` | Auth | PIN/admin actions | resident and committee verification |
| `resident_signatures` | Residents/polls | resident signature flow | voting/audit flows |
| `admin_access` | Auth | `adminAccessMatrix` | all committee/admin handlers |
| `audit_log` | Operations | auth/admin flows | admin audit actions |
| `lifestyle_surveys` | Surveys | survey update API | resident/admin survey APIs |

`residents` is a shared kernel collection. Changes can affect LPR, profile,
payment, visitor, and admin applications, so it must not be owned by a single UI.

## LPR and operational reporting

| Collection/document | Purpose |
|---|---|
| `lpr_traffic_events` | Canonical vehicle movement events |
| `lpr_vehicle_profiles` | Derived/known vehicle profile data |
| `lpr_reconciliation_runs` | LPR vs resident-data reconciliation results |
| `lpr_daily_traffic_reports` | Daily derived traffic reports |
| `lpr_overnight_reports` | Overnight derived reports |
| `lpr_unreadable_labels` | Human labels for unreadable captures |
| `lpr_agent_c_camera_status` | Camera status/probes |
| `lpr_agent_c_event_audits` | Per-event Agent C audit |
| `lpr_agent_c_daily_metrics` | Daily Agent C metrics |
| `lpr_agent_c_report_audits` | Agent C report audit records |
| `lpr_agent_c_alerts` | Deduplicated alerts |

The canonical/derived distinction should be preserved: `lpr_traffic_events` is
event data; daily/overnight/Agent C report collections are projections. Report
rebuilds must not mutate canonical events unless an action explicitly edits a
human label or correction.

## System configuration

Configuration lives under `system_config/*`, including `line`,
`line_flex_routing`, `lpr_monitor`, `daily_traffic`, `security_shift`,
`guard_audit`, `lpr_agent_c`, `visitor_intake`, `visitor_daily`, and
`bulky_waste_round`. Each config document needs a named owner and validator when
its domain is extracted.

## Query and performance review

Verified complete collection reads currently include resident aggregation/sync,
PIN/admin matrices, lifestyle stats, some payment resident resolution, and some
poll vote/report paths. At 68 houses these may be acceptable; optimize only after
measurement. The higher-value improvements are:

1. Avoid repeating the same full resident read within one request or batch.
2. Resolve a resident by normalized document key when the key is available.
3. Keep report queries bounded by date and indexed.
4. Replace per-payment full resident scans with a request-scoped resident map or
   direct document lookup.
5. Declare every production composite query in `firestore.indexes.json`.

Only one composite index is currently checked in: visitor logs by `houseNo` and
descending `createdAt`. Emulator/query tests should be added before changing
indexes or query shapes.
